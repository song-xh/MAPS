# 05｜轻量 Demo 实施与投稿准备

修订：2026-09-21。按两标签页的演示范围实施，不再执行上一版8–10周完整平台建设计划。

## 1. 实施顺序

| 步骤 | 完成内容 | 做到什么即可进入下一步 |
|---|---|---|
| 1 页面与加载 | Dash两标签页、数据和算法选择、RL模型加载 | 一份小数据和一个兼容模型能加载，地图出现 |
| 2 算法接入 | 直接调用CAPA/RL-CAPA，整理帧与结果 | 运行得到真实结果；少量演示任务有候选、竞价、动作记录 |
| 3 动态演示 | 播放、暂停、单步、重置、滑条、详情联动 | 能跟随一个包裹看完过程；预计算记录也能播放 |
| 4 图表与美化 | TR/CR/BPT、收益曲线、批次统计，统一样式 | 结果与原输出一致，两页清楚可读 |
| 5 演示准备 | 选好示例、检查模型与方法说明、录屏和启动说明 | 别人按说明可以完成加载→回放→图表 |

熟悉现有Python算法、已有可用模型和数据时，可按约10–15个工作日作初始预算；不是承诺工期。若尚缺可用模型或过程记录，单列适配/记录工作，不因工期倒推假过程。论文与算法修订、重新训练不计入纯页面工期，也不要求全部搬进demo。

先完成CAPA链路，再接RL-CAPA；这是实现次序，最终仍保留用户所需的模型加载和RL展示。基线数量与训练曲线按实际演示需要增加。

## 2. 准备三类文件即可

1. **小数据示例**：适合看清任务、courier、平台和路线，计算时间适合现场等待。
2. **模型文件**：一个已验证兼容的RL-CAPA模型及normalizer/配置，用于推理。
3. **演示结果**：一份完整过程回放；按需附一组对比CSV/JSON和一份训练日志。

大规模结果用原项目脚本预先计算和整理。demo只负责加载，不开发多seed调度、自动扫描、实验库或模型训练功能。已有summary无法说明过程时，需要提前增加记录并重跑指定小场景，不能从汇总数值编造中间步骤。

## 3. 演示脚本

建议用约3–5分钟串起两页，具体时间可按最终投稿要求调整。

| 步骤 | 操作 | 展示重点 |
|---|---|---|
| 加载 | 选数据、选CAPA或RL-CAPA，必要时加载模型 | 输入与方法是什么 |
| 运行/回放 | 点开始运行，或明确加载已有回放 | 任务如何按批次进入算法 |
| 查看过程 | 暂停、选包裹、单步看本地匹配和双层竞价 | 为什么这样分配、谁获胜、支付多少 |
| 查看RL | 切到RL详情 | 批长和包裹去向的两阶段决策 |
| 看图表 | 切结果标签页，可选加载对比结果 | 收益、准时完成率、耗时及方法权衡 |

无需展示登录、创建项目、登记实验或管理模型。允许结果不占优，用过程解释原因，不要求每次演示都得出“RL全面最好”。

## 4. 保留必要验证，移除平台验收

只验证展示链路：加载正确、模型兼容、播放联动、指标一致、竞价顺序/支付正确、真实来源说明、演示电脑上可用。加入过程记录后，检查指定示例的分配和收益没有因此改变。

原审查提出的CAMA/KM差异、RL动作及五网络差异、oracle输入、估算数据等仍是事实问题。对选定演示版本作准确说明，避免UI与代码不一致；与本次场景无关的大规模实验问题不作为页面开工前置条件。[审查附件](research/algorithm-evidence.md)

如果论文主张算法普遍更优，仍应在原实验项目完成公平比较与必要重复试验。**这是论文证据工作，不等于demo需要实验管理、在线训练或自动评测功能。**

## 5. 投稿材料保持精简

目标仍是VLDB/PVLDB Demonstrations Track。2026-09-20核验的2026规则为包含全部材料的4页，鼓励不超过5分钟/50MB视频；实际投稿前核对目标年度Demo CFP，不套用Research Track规则。[2026官方要求](https://www.vldb.org/2026/call-for-demonstrations.html)

稿件围绕问题、算法展示方法、简短架构和观众操作场景组织，主要截图就是两页。投稿卖点可以是“一件包裹的本地匹配、双层竞价、RL选择与结果在同一界面串联”，不必夸大为通用数据管理平台。

交付包只需：可运行demo、依赖清单、授权范围内的示例数据、模型、回放文件、启动说明和演示视频。对比/训练曲线按论文需要附上。静态设计稿不作为已实现系统截图。
